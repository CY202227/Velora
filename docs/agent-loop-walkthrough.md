# Velora Agent Loop：一次请求如何被执行

Velora 的 Agent Loop 是围绕模型运行的一套控制程序。模型根据上下文决定回答或调用工具；运行时负责准备输入、执行工具、控制资源、记录进度，并决定本次执行如何继续或结束。

当前所有会话使用同一个统一驱动。默认没有固定四轮、24 步或任务总时长限制；部署方可以显式设置预算。模型不同不会改变生命周期规则，但模型容量、Token 计量和接口适配可能不同。

下面沿着一次请求解释当前实现。本文描述已有代码，不把扩展接口当作已经上线的业务功能。

## 1. 先分清会话、回合、步骤

**会话 Session** 保存多次交互的业务环境，例如角色、历史和模型设置。

**回合 Turn** 是一次用户请求经过加载上下文、模型执行、后处理与保存的完整过程。

**步骤 Step** 是一次模型请求，以及这次请求产生的工具批次。一批可能包含多个工具。网络暂时失败后的请求重试，不算新的业务步骤。

例如，用户要求先查资料再总结。模型先调用检索工具，收到结果后再回答，这通常是两个步骤，属于同一个回合。

恢复会创建新的运行 ID，并保留原目标和累计进度。运行 ID 用来追踪执行，不应与会话 ID 或最终保存的对话记录 ID 混为一谈。

## 2. 请求先进入业务处理链

当前请求可以从终端或后端接口进入：

```text
终端 / 调用方
    ↓
TurnRouter
    ↓
LoadContext → RecallMemory → ComposePrompt
    ↓
LLMNode → AgentLoop
    ↓
PostProcess → PersistTurn → EmitReply
    ↓
turn_end
```

`TurnRouter` 管理会话调度。同一会话的回合串行执行，避免同时改写历史；取消使用独立通道，不等待当前会话锁。

前三个节点加载会话和角色、召回长期记忆，再将材料组装成模型输入。模型阶段结束后，成功路径继续后处理、保存与回复发布。

这条业务链规定请求有哪些阶段。真正反复调用模型的循环位于 `AgentLoop` 中。

## 3. TurnContext 和 RunState 分别保存什么

`TurnContext` 是整个业务回合共享的工作台，包含请求、角色、记忆、模型配置、最终回答，以及事件发布和检查点保存入口。

`RunState` 专门描述模型阶段：消息历史、当前阶段、步骤编号、Token 用量、压缩档案、工具执行记录、恢复计数和终态。

因此，角色与长期记忆属于业务上下文；模型执行到第几步、哪个工具结果未知，属于运行状态。共享的节点对象只保存配置，不保存某个用户的执行进度。

## 4. 模型阶段先建立执行状态

普通请求从已组装的消息创建独立 `RunState`。恢复请求则从持久检查点恢复消息和累计计数，同时重载当前连接配置；模型不一致时拒绝恢复。

驱动为本次请求准备 Provider，设置输出预留。提供方实例按运行需要复制，避免一次请求的输出配置污染其他会话。

此时尚未认定任务完成，只是准备好进入下一步。

## 5. 每次请求前先判断能否安全继续

驱动在每一步之前执行准入检查：

1. 若显式配置了步骤预算，检查是否耗尽。
2. 确认模型上下文窗口容量。
3. 计算本次完整消息与工具定义的输入占用。
4. 为模型输出预留空间。
5. 必要时裁剪或压缩历史。
6. 写入 `request_ready` 检查点。
7. 发出模型请求。

容量优先使用配置；否则查询单模型元数据，不支持时回退到模型列表并严格匹配模型 ID。若无法确认容量，明确报告失败，不凭空假定窗口大小。

计量扩展可用时采用服务端结果；否则纯文本使用保守估算，并记录计量来源。累计消耗与当前上下文占用分开：同一段历史可能被多次发送，而压缩又会缩小当前输入。

图片等非文本输入不能通过 URL 长度估算成本。缺少对应计量能力时，不允许静默漏算后继续请求。

## 6. 上下文不足时，如何压缩

压缩在消息副本上进行，原消息不会立刻被修改。

首先裁剪较早、过大的工具结果，保留最新证据。若仍然超预算，再选择一段完整、闭合的旧历史，单独请求模型生成摘要。

系统指令、当前用户输入和最新工具批次受到保护。工具调用与结果必须配对，不能保留调用却删掉对应结果。

摘要返回后，驱动检查它是否非空、没有工具调用或显式推理标签、没有截断，并且确实缩小上下文、满足预算。还要确认等待摘要期间运行状态没有变化。

只有检查通过，才一次性替换消息，并保留压缩前档案。摘要失败、取消或无效时不覆盖原历史。若摘要源本身都放不进窗口，当前实现会停止，而非无限尝试压缩。

当前不把带媒体的历史片段序列化成文本后假装完成媒体摘要。

## 7. 模型请求有三个主要出口

模型生成的文字通过 token 事件实时发布，但这时仍可能是草稿。完整响应返回后，驱动根据结果分流。

**返回工具调用**：进入工具执行阶段。

**返回完整文字且没有工具调用**：进入结束检查阶段。

**返回异常、截断或过滤结果**：按对应错误处理。非空的半截回答也不能作为成功答案保存。

暂时网络故障及部分服务状态支持有限重试，默认最多额外两次。重试前通知客户端重置草稿，避免把失败请求的文字与新结果拼接。

网络重试只重试模型请求，不重放已执行工具。输出截断目前明确失败，尚未自动续写。

## 8. 模型提出工具调用，运行时执行工具

工具定义由前置提示词装配阶段提供，模型从本次可见集合中选择。当前循环沿用这份集合；尚无通用的按需工具搜索流程。

执行时先记录模型的工具调用消息，并建立本批工具状态，再逐个执行：

```text
not_started
    ↓ 保存启动检查点
running
    ├─ 返回结果 → returned
    ├─ 执行异常 → failed
    └─ 取消或无法确认 → result_unknown
```

工具启动检查点必须写入成功，才允许派发实际调用。这样，重启后看到未闭合的执行记录时，可以保守地标为结果未知。

工具目前串行执行。结果写入账本并追加到模型消息，下一步模型据此决定继续行动或回答。

`returned` 只表示拿到返回值，返回值本身可能包含业务错误。模型可以改参数再试；相同调用连续三次返回相同错误时，驱动停止，避免持续空转。成功轮询不会仅因参数重复而被拦截。

目前保护主要覆盖连续相同错误，并不等于已经能识别所有业务无进展。

## 9. 没有工具调用，也不一定马上结束

驱动检查回答非空，再执行已注入的结束策略。策略返回类型化决策，由驱动统一处理：

- `finish`：允许结束模型阶段。
- `continue`：附具体缺项反馈，再次请求模型。
- `wait`：等待补充输入。
- `stop`：停止执行。

停止优先于等待，再处理继续。空反馈不能要求继续；自动强制继续默认最多三次，每个策略调用也有超时。

例如验收器发现文件缺失，可以反馈“尚未找到输出文件，请生成并检查”，让模型执行下一步。缺少收件人则可以等待用户补充。

**当前生产装配默认没有具体业务验收器。** 接口和保护已实现，但普通路径仍主要依据完整非空回答且没有工具调用收尾，不能据此宣称所有任务都已经过产物验收。

## 10. 模型阶段结束后，业务链如何继续

`LLMNode` 将模型阶段结果转换为业务链控制结果。

只有 `completed` 才继续后处理、对话保存和最终回答发布。`failed`、`waiting` 或 `cancelled` 会停止成功路径，避免将未完成提示当作助手答案写入长期记忆。

最终对话保存使用运行 ID 派生稳定记录 ID。相同运行重复保存不会新增同一组记录；内容冲突要报错。记忆交付继续使用稳定回答 ID 作为幂等依据。

这不提供外部工具的全局 exactly-once 保证。发送、支付或远程写入等操作仍需工具侧幂等键或结果查询。

## 11. 预算耗尽，也必须正确返回

默认没有任务级步骤与总时长限制；若部署方显式配置预算，耗尽后返回未完成终态，而不是让模型编造收尾。

正常可写连接最终收到 `turn_end.result`，其中包括状态、原因、可读说明、运行 ID、步骤及工具进度计数。

例如：

```json
{
  "status": "failed",
  "reason": "step_budget_exhausted",
  "message": "任务尚未完成：已达到本次执行步数预算。",
  "run_id": "…",
  "step": 10,
  "tools_returned": 3,
  "tools_result_unknown": 0,
  "resume_supported": false
}
```

终端显示这个未完成说明，单次命令返回非零退出码。HTTP 200、收到过文字或工具返回成功，都不能代替终态判断。

若连接已经断开或进程崩溃，无法保证终态送达，调用方应查询持久检查点。当前失败终态也不自动意味着允许直接恢复。

## 12. 检查点怎样支持恢复

请求前、工具执行前后、模型结束和处理链退出都会保存边界。检查点和对应事件在同一事务提交，带 schema_version、revision 与运行 ID。

恢复通过 `/api/chat/resume` 进入。流程是读取源检查点、判断安全性、用版本比较原子认领、同事务创建后继，再继续模型执行。

同一源只有一个认领者成功，旧运行无法覆盖已转交记录。后继有独立运行 ID，继续原目标，并保留累计进度。

当前可恢复的主要是工具结果完整的请求前边界，以及补充输入后的 waiting。结果未知、非安全工具边界、已结束、已认领或内容被脱敏而无法可靠恢复的记录会被拒绝。

恢复不是从任意代码行接着跑。模型已结束而后处理执行到一半等位置，当前不开放任意重跑。

## 13. 当前系统的能力边界

这套 loop 已有统一调度、请求准入、文本摘要、有限网络重试、工具状态、结束策略接口、正确终态和安全检查点恢复。

仍需继续完善具体业务验收器、服务端溢出恢复、截断续写、完整媒体摘要、工具超时与副作用故障策略，以及生产故障注入和数据保留策略。

因此，当前最准确的描述是：**Velora 已有可追踪、可取消、能从安全边界恢复的模型执行循环；业务任务是否完成，还需要与任务对应的验收依据。**
